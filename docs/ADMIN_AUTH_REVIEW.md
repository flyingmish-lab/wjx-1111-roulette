# WJX: проверка новой авторизации

Изменения подготовлены в ветке `feat/browser-admin-auth`. Пользователь подтвердил публикацию и дополнительно запросил назначение тестовых попыток выбранным пользователям.

Серверная часть опубликована: `wjx-admin-auth` проверяет конфигурацию Secrets, `rapid-action` отвечает `410`, миграции применены, `wjx-roulette` отвергает административные запросы без парольной сессии. Транзакционная проверка подтвердила сохранение существующих записей участников, реальных и тестовых прокруток. Значения Secrets не читались. Проверка сохранности выполняется через локальные SQL-переменные без создания дополнительной таблицы.

## Что проверено в действующем проекте

19 ноября 2026 года изучены публичный репозиторий, опубликованный исходник `wjx-roulette`, код `rapid-action` и метаданные PostgreSQL проекта `xfslymkzlzfsrzaoerpn`. Значения Secrets не открывались и не копировались.

- Исходная рулетка выделяет два Telegram ID, обходит для них расписание и использует `wjx_test_spins` / `wjx_save_test_spin`.
- Исходные административные операции доверяют проверенному Telegram ID.
- `rapid-action` опубликована и сравнивает общий пароль, но не ограничивает попытки и не создаёт сессий. Оставлять этот параллельный способ проверки пароля при выпуске новой авторизации нельзя.
- У шести существующих таблиц включена RLS, политик в `public` нет. Настройки и попытки входа уже закрыты от `anon` и `authenticated`; у остальных таблиц есть табличные GRANT, доступ блокируется RLS.
- SQL-функции сохранения попыток доступны только `service_role` и владельцу базы. Реальная попытка уже защищена advisory lock по Telegram ID.

## Подготовленное поведение

Админ-панель остаётся по адресу `/wjx-1111-roulette/admin.html`, открывается в обычном браузере и не загружает Telegram SDK. Вход — через `wjx-admin-auth`, административные операции — через `wjx-roulette`. Все административные API настроек и статистики требуют `Authorization: Bearer <session>` на сервере.

Сессия действует один час, подписана HMAC-SHA-256, содержит случайный идентификатор из 32 байт и привязана к обоим секретам. В базе хранится только SHA-256 токена. Каждый административный запрос проверяет подпись, срок и наличие активной записи. Выход удаляет только запись текущей сессии. Смена любого секрета делает прежние токены недействительными. При недоступности базы или неверной конфигурации доступ закрывается.

Пароль и токен не сохраняются в `localStorage`, `sessionStorage`, URL или логах. Токен живёт в памяти вкладки: обновление страницы требует повторного входа. При сетевой ошибке выхода интерфейс очищается, но серверный токен может оставаться действующим до истечения часа; интерфейс сообщает об этом.

На общий пароль допускаются 10 запросов входа за 15 минут. Счётчик резервируется транзакционно до проверки пароля; успешные входы тоже учитываются и не сбрасывают лимит. Ответ `429` содержит `Retry-After`. Лимит общий для всех устройств, не зависит от заголовков IP, защищает также от распределённого перебора. Компромисс: злоумышленник может временно исчерпать лимит входа для всех. Уже выданные сессии при этом продолжают работать.

Сервер требует пароль длиной не менее 12 символов и секрет сессий длиной не менее 32 символов. Рекомендуется случайный длинный пароль и криптографически случайный секрет. Их фактические длина и случайность в боевом окружении не проверялись: значения не читались. Если требования не выполнены, вход вернёт общее сообщение о недоступности, без раскрытия секретов.

Все Telegram-пользователи проходят одинаковую проверку подписи и срока `initData`, используют `wjx_spins` и один дневной лимит. Расписание дополнительно проверяется внутри SQL-транзакции сохранения. Административная сессия не даёт игровых привилегий.

Сохранены даты, время по Москве, число попыток, шесть призов, проверка суммы вероятностей, реальные выигрыши, архив тестовых выигрышей и история последних 50 реальных прокруток. Статистика агрегируется в PostgreSQL без ограничения первыми 1000 строками. Имена и призы выводятся как текст. `test_mode` и старые тестовые записи остаются в базе для совместимости и истории, но не участвуют в правилах. Старый сброс тестовых попыток удалён, исполнение старой тестовой SQL-функции отзывается у `service_role`. По дополнительному запросу пользователя добавлено управляемое тестирование: администратор ищет зарегистрированного участника и устанавливает остаток 0–100 в отдельной таблице `wjx_test_balances`. Новая `wjx_use_test_spin` атомарно уменьшает только этот остаток и записывает результат в `wjx_test_spins`; реальная игра и её лимиты не затрагиваются. В Mini App отдельная тестовая кнопка работает вне дат акции, показывает пометку «без выдачи призов» и не добавляет результаты в историю призов к получению. Остаток действует до расходования или изменения администратором, автоматически по дням не восстанавливается.

## Проверки

Запуск: `npm ci`, `npm test`, `npm run check` (Node.js 24). Итог: все 19 тестов и проверка типов трёх Edge Functions прошли.

- Реальное исполнение миграции в локальном PostgreSQL через PGlite, повторное применение, сохранение старых данных и проверка GRANT/RLS.
- Исчерпание и восстановление лимита входа; 30 запросов дают ровно 10 разрешений.
- Одинаковые дневные лимиты для владельца, сотрудника и обычного пользователя; запрет вне расписания и с подменённой датой.
- Агрегация более 1200 записей и ограничение истории 50 строками.
- Подпись, случайность, истечение срока, ротация секретов, отзыв сессии и отказ при сбое базы.
- Все четыре административных API: запрет по одному Telegram ID, без токена, с поддельным/истёкшим/отозванным токеном; разрешение с действующей сессией без Telegram.
- Серверная валидация дат, времени, дневного лимита, состава и вероятностей призов.
- DOM-проверки входа, сохранения настроек/вероятностей, статистики, выхода, очистки данных и безопасного вывода имён.
- Проверка типов Edge Functions настоящим Deno.

Ограничения: обработчики API проверялись с подменой транспорта Supabase, SQL — на локальном PostgreSQL по изученной схеме, интерфейс — в jsdom. PGlite выполняет запросы последовательно; проверка 30 запросов не заменяет нагрузочный тест нескольких соединений Supabase. Транзакционные блокировки сохраняются в SQL. Боевой сквозной вход и Telegram Mini App нужно проверить после согласованного выпуска: новую функцию нельзя испытать в production до её публикации.

## Порядок выпуска — только после подтверждения

1. Убедиться, что секреты отвечают требованиям выше, не раскрывая значения. При необходимости владелец самостоятельно меняет их в Supabase. Перед выпуском сохранить резервную копию действующего серверного кода и базы средствами Supabase.
2. Опубликовать подготовленную `rapid-action`, которая всегда отвечает `410` и больше не проверяет пароль. Это закрывает обход ограничения перебора без удаления функции.
3. Применить обе миграции из `supabase/migrations` по порядку. Для редактора Supabase подготовлен общий транзакционный файл `dashboard-dist/release.sql` с проверкой сохранения числа существующих записей. Она не удаляет существующие игровые/административные записи и не меняет вероятности, расписание или дневной лимит.
4. Опубликовать `wjx-admin-auth` и обновлённую `wjx-roulette` вместе с общей папкой `_shared`. `verify_jwt = false` нужен для собственной проверки Telegram-подписи и административной сессии; проверки выполняются в коде. Точные настройки находятся в `supabase/config.toml`.
5. После проверки API опубликовать `admin.html`, `admin.js` и `index.html` через текущий GitHub Pages. До этого старый админ-интерфейс временно не сможет управлять проектом: доступ через Telegram уже будет закрыт.
6. Владелец самостоятельно проверяет правильный пароль в браузере. Проверить получение настроек/статистики, выход и отказ при повторном использовании отозванного токена. Не менять действующие шансы или даты ради проверки; запись настроек уже испытана локально.
7. Проверить обычный `status` из Telegram и одинаковые ответы для всех участников. Не выполнять реальные призовые прокрутки ради теста и не сбрасывать существующие попытки.

Выпуск серверной части выполнен через Supabase Dashboard; исходники и страницы публикуются в этот репозиторий через GitHub.

## Восстановление

Если новый вход недоступен, сначала проверить настройки публикации функций, выполнение миграции и наличие/длину Secrets; не возвращать Telegram-права и парольный oracle `rapid-action`. Миграция добавляет объекты и сохраняет существующие данные, поэтому для исправления не требуется откат с удалением таблиц. Возможен временный запрет административного доступа до исправления с сохранением игровой части.
