# Подписка и подготовка запуска WJX Рулетка

Подготовлено 20 ноября 2026 года. Публикация подтверждена пользователем. Миграция 006 применена 20 ноября с проверкой сохранности записей [3 участника, 3 реальные прокрутки, 18 тестовых], дат, настроек и вероятностей. Обновлённые API и обработчик бота опубликованы 23 ноября. Сайт и проверки GitHub публикуются тем же выпуском. Реальный доступ бота к каналу проверяется после входа в новую админку; до этой проверки не считать его подтверждённым. Даты и призы этим выпуском не менялись.

## Подписка

Обязательный канал: `@tattoowjxrussia`, ссылка `https://t.me/tattoowjxrussia`. Перед каждой НОВОЙ реальной или тестовой прокруткой сервер вызывает Telegram `getChatMember`. ID берётся исключительно из проверенного `initData`, параметры `user_id` и `subscribed` клиента не используются. Приняты статусы `creator`, `administrator`, `member`; `restricted` — только с `is_member=true`. Владелец и сотрудник не получают исключений. Положительный ответ не кешируется между новыми прокрутками: отписавшийся снова получит отказ.

`left` и `kicked` дают 403 `SUBSCRIPTION_REQUIRED` до выбора приза и SQL-списания. Ошибка Telegram, 429, недоступность, неизвестный статус или несовпадение user.id дают безопасный 503 без нового результата/списания; детали исходной ошибки, URL с токеном и секреты не выводятся.

При отказе Mini App показывает «Открыть канал» и «Я подписался — проверить». Повторная проверка выполняется на сервере и сама не расходует попытку. Сохранённая операция с тем же UUID возвращается без новой проверки подписки: так отписка или сбой Telegram не скрывают уже записанный результат. Статус, история и обращение за реальным призом доступны без подписки.

`/rules` сообщает условие подписки. Информации о тестовых попытках в пользовательском интерфейсе и ответах бота по-прежнему нет.

В админке добавлена «Проверить доступ бота к каналу»: `admin_subscription_status` требует парольную сессию, читает `getMe` и `getChatMember` самого бота, проверяет ID и статус администратора. Он не назначает права и не публикует сообщения.

Для надёжной проверки других пользователей Telegram требует, чтобы бот был администратором канала. Пользователь должен самостоятельно добавить `@wjx_1111_roulette_bot` в администраторы `@tattoowjxrussia`. Наличие этих прав в production пока не проверено. Администратор канала — это техническая роль бота, а не особые игровые права Telegram-пользователей.

## Оптимизация и пауза

Миграция `202611200006_launch_readiness.sql`:

- Добавляет `spins_paused=false` без изменения дат и остальных настроек.
- Вводит закрытую RPC `wjx_register_player`: создаёт профиль и обновляет имя/ник только при изменении. Повторные запросы продолжают обращаться к БД, но не создают лишние версии одинаковых строк. Проверено сохранение `ctid` и `joined_at` при повторном идентичном вызове.
- Добавляет паузу в авторитетную транзакцию новой прокрутки, включая тестовую, под разделяемой блокировкой строки настроек. Проверка после поиска уже сохранённой операции сохраняет восстановление UUID. Отказ `P0003` не списывает баланс.
- Возвращает паузу в состоянии игрока. Существующие записи сохраняются; повторное применение не сбрасывает включённую паузу.

`admin_set_pause` требует парольную сессию и boolean, меняет только паузу. Отдельная кнопка админки не сохраняет и не сбрасывает черновик дат в форме. Игрок видит понятное сообщение; история, статистика, выдача и восстановление ранее сохранённой операции остаются доступны. При новой игровой операции серверная проверка действует даже со старым/модифицированным клиентом. Ранее начатая транзакция может завершиться до вступления изменения паузы в силу; пауза не отменяет зафиксированные результаты.

Опрос состояния заменён на адаптивный таймер: 60–69 секунд в активной игре, 300–345 секунд до старта/после окончания/после исчерпания попыток. Скрытая вкладка не опрашивает сервер; возврат и восстановление сети обновляют состояние. Таймер учитывает ближайшее начало события и московскую полночь. При паузе опрос остаётся частым, чтобы заметить возобновление. Небольшой случайный сдвиг распределяет запросы; он не используется для выбора призов.

Проверка подписки не вызывается фоновым опросом и не создаёт постоянных Realtime-соединений. На каждую новую прокрутку появляется один дополнительный внешний запрос Telegram. Пики/429 Telegram остаются внешним ограничением; автоматическое разрешение игры при сбое не предусмотрено.

## Проверки и границы

- `npm test` и `npm run check`: новые проверки членства, отказов Telegram, серверной идентичности, паузы, восстановления, UI и SQL плюс существующие регрессии.
- 100 одновременно запущенных локальных обработчиков `status` с искусственными Telegram-подписями: правильные независимые ID, 100 регистрационных RPC, отсутствие списаний. Это тест логики с подменённой БД/транспортом, НЕ подтверждение пропускной способности Supabase NANO.
- `node scripts/capacity-audit.mjs` повторно выполнен с шестью миграциями, 3 000 искусственных участников, 9 000 прокруток и 9 000 операций. Сводки работают; 100 повторов не списали лишние попытки. SQL проверялся локально в последовательном PGlite, не в облаке с конкурирующими соединениями.
- Для настоящего пика до 100 пользователей нужен отдельный стенд и измерение сквозных p95/таймаутов/блокировок. В рабочем проекте искусственные выигрыши не создавались.
- Добавлен GitHub Actions `Validate roulette`: Node 24, npm ci, все тесты, typecheck; права только чтения репозитория, без боевых секретов. В удалённом GitHub workflow ещё не запущен, поскольку публикация не согласована.

## Перед выпуском

1. Пользователь добавляет бота администратором канала. После обновления API проверить диагностикой, что `ready=true`; до направления участников проверить реальную подписку/отписку на своём аккаунте.
2. Сделать действительную резервную копию БД (структура, данные, роли), сохранить вне публичного GitHub и проверить восстановление в ОТДЕЛЬНОЙ базе. Инструкция Supabase: https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore . Не сбрасывать пароль БД без отдельного решения; существующие данные и рабочую БД для проверки восстановления не очищать. Секреты Edge Functions сохраняются отдельно владельцем; их значения не нужны в переписке. Полноценная производственная резервная копия и её восстановление в рамках этой подготовки ещё не выполнены: требуется отдельный доступ к дампу/соединению БД.
3. Получить подтверждение публикации. Сначала миграция 006, затем собранные `wjx-roulette` и `wjx-telegram-bot`, затем сайт/admin.js с обновлённой версией URL. Миграция совместима со старым API; новый API требует новой RPC и не должен развёртываться раньше миграции.
4. Проверить закрытый доступ без админ-сессии, статус игрока, подписчика, неподписчика, паузу, безопасный отказ при ошибке Telegram и отсутствие изменения существующих призов. Реальные призовые прокрутки выполняет пользователь.
5. Окончательные три календарных дня задаёт пользователь. Запас призов не ограничивался автоматически; существующие проценты сохраняются.

Официальный Bot API: https://core.telegram.org/bots/api#getchatmember .

20 ноября отдельно сохранена копия public-схемы приложения: все 10 таблиц и их записи, структура колонок, ограничения, индексы, последовательности, права таблиц/функций/последовательностей, RLS/политики, триггеры и 12 SQL-функций. Точное совпадение записей после восстановления проверено в отдельной локальной PGlite. Архив хранится отдельно от публичного репозитория; в GitHub публикуются только `scripts/backup-export.sql` (SELECT) и `scripts/verify-app-backup.mjs` (проверка исключительно в памяти, без сетевого доступа). Архив и данные пользователей не входят в этот коммит.

Это резервная копия данных приложения, а не полный дамп проекта Supabase: Auth, Storage, платформенные настройки и Supabase Secrets в неё не входят. Их полное восстановление этой проверкой не подтверждалось. Проверка облачной нагрузки до 100 реальных одновременно активных пользователей также остаётся отдельной задачей; локальные тесты её не заменяют.
