# Проверка перед запуском WJX 11.11

Проверено 20 ноября 2026 года. Изменения игры, настроек, прав и данных не публиковались. Запросы к рабочей базе были только SELECT; секреты не открывались. Боевые призовые прокрутки не выполнялись.

## Решение о готовности

Основная защита и обычные сценарии работают. До массового запуска рекомендую исправить восстановление игры при сбоях сети и подтвердить окончательные даты. Успешные тесты обычных сценариев не покрывают найденные ниже сбои.

## Что исправить до запуска

### 1. Потерянный ответ после сохранения прокрутки — высокий приоритет

Сервер сохраняет выигрыш до отправки HTTP-ответа. Если ответ теряется, игрок видит ошибку, хотя попытка уже потрачена. Повторное нажатие отправляет новую прокрутку: общего идентификатора операции нет. Это не обход дневного лимита, но может расходовать следующую попытку и скрывать первый результат в интерфейсе.

В изолированной проверке: после потери первого ответа сохранена одна прокрутка и показана ошибка; после ручного повтора сохранены две, а локальная история содержит один результат.

Решение: уникальный идентификатор операции, повтор с тем же ID возвращает сохранённый результат; защита дубликатов внутри SQL-транзакции. После сомнительного сетевого исхода — восстановление состояния из базы. Не повторять автоматически неидемпотентный запрос.

Источники: `index.html` — `requestServerSpin`, `playSpin`; `supabase/functions/wjx-roulette/index.ts` — действие `spin`; `wjx_save_spin` в миграции 001.

### 2. Загрузка состояния может оставить игру нерабочей — высокий приоритет

При старте выполняются регистрация и два запроса `status`. Первый загружает счётчик, второй — расписание. При ошибке первого второй может успешно загрузить расписание, но `serverStatusLoaded` остаётся `false`: прокрутка молча прекращается. При ошибке второго первый уже разблокировал игру, но расписание остаётся встроенным в HTML, отличным от базы. Нет явной кнопки повторной загрузки или ограничения времени ожидания запроса.

Оба частичных сбоя воспроизведены в изолированном DOM. Решение: один согласованный ответ состояния с расписанием, загрузка/ошибка/повтор в интерфейсе, ограничение времени ожидания. При возврате во вкладку обновлять состояние и учитывать время сервера.

Источник: `index.html` — `loadServerStatus`, `loadRouletteSettings`, инициализация страницы.

### 3. История игрока зависит от памяти устройства — средний приоритет

Сервер возвращает число выигрышей, но не сами призы. На новом устройстве или после очистки хранилища у игрока с реальными выигрышами показаны `1. — 2. — 3. —`. Админка видит правильные призы, а кнопка обращения к менеджеру определяется сервером, поэтому выигрыш в базе не теряется.

Решение: возвращать игроку его собственную серверную историю/сводку, используя ID только из проверенных Telegram initData. Локальное хранилище оставить необязательным кешем. Это также устранит путаницу между Telegram-аккаунтами в одном браузере.

### 4. Повреждённое хранилище останавливает JavaScript — средний приоритет

`JSON.parse` для `wjxSpins` и `wjxEventHistory` не защищён. Некорректный JSON вызвал `SyntaxError` и остановил инициализацию. Значения корректного JSON тоже не проверяются по типам.

Решение: безопасное чтение и проверка формы данных, работа без доступного localStorage. Ошибка записи кеша не должна мешать показу результата, уже сохранённого сервером.

### 5. Переход через полночь и часы устройства — средний приоритет

`todayKey` вычисляется один раз при открытии. В проверке после московской полуночи текущая дата стала 28 ноября, а ключ сохранения остался 27 ноября. Счётчик и локальная история не синхронизируются автоматически при смене дня. Сервер продолжает правильно ограничивать попытки по текущей московской дате.

Также состояние «до/после розыгрыша» вычисляется по часам устройства. Неверные часы могут преждевременно показать завершение или скрыть доступную игру, хотя серверная проверка не позволит незаконную прокрутку.

Решение: серверное время/состояние периода, обновление при смене дня, возврате в приложение и восстановлении сети.

## Улучшения процесса выдачи и эксплуатации

- Карточка участника подтверждает выигрыш, но не выдачу. Добавить отметку «выдано», дату, количество и журнал; повторная обработка не должна выдавать те же призы второй раз. До этого вести отдельный реестр выдачи. Ник и отображаемое имя не заменяют сверку реального отправителя по Telegram ID.
- Добавить общий аварийный переключатель паузы реальных прокруток, сохранив доступ к истории и обращениям к менеджеру.
- Перед запуском сохранить резервную копию базы и проверить возможность восстановления; наличие актуальной резервной копии в этой проверке не подтверждалось.
- Проверить одновременные запросы и ожидаемую нагрузку в отдельном тестовом окружении. Не создавать искусственные выигрыши в production.
- Добавить CI для `npm test` и `npm run check`. Сейчас проверенная публикация GitHub Pages не заменяет автоматический запуск этих проверок при каждом изменении.
- Тестовые остатки сейчас нулевые. Проверить это ещё раз перед стартом, если до него будут дополнительные тесты.
- Сократить начальные запросы и повторные чтения базы. Для большой аудитории полезны индексы истории/статистики после проверки планов запросов. Сейчас у реальных прокруток есть индекс `(telegram_id, spin_date, spin_number)`; нехватка производительности на текущем объёме не установлена.
- Уточнить подписи расписания: в браузере без Telegram сейчас видны встроенные даты 22–28 ноября; даже во время активного периода формируется надпись «начнётся». Показывать понятное приглашение открыть Mini App через Telegram.
- В общем пароле входа действует глобальный лимит 10 запросов за 15 минут. Это защищает перебор, но его можно исчерпать для всех администраторов. Выданные сессии продолжают работать; это известный компромисс, а не обнаруженный обход авторизации.

## Ограничения проверки

Дополнительные сценарии выполнялись в jsdom с искусственным транспортом, а SQL-тесты — на PGlite. Они не являются нагрузочным тестом нескольких соединений Supabase. Сквозной повторный вход по боевому общему паролю, Telegram на физических iPhone/Android, менеджерский процесс выдачи и восстановление резервной копии сейчас не проверялись. Успешный пользовательский тест ранее подтверждён владельцем проекта.

Диагностика воспроизводится командой `node scripts/prelaunch-audit.mjs`. Она использует искусственные данные из тестового набора, не обращается к рабочему API и не выполняет боевые прокрутки. Производственный код в ходе этого аудита не изменён.
